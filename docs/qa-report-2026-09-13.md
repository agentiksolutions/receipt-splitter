# Halfsies browser QA, 2026-09-13

Browser end-to-end pass against a dev server on `localhost:5260`, driven through Chrome at
emulated phone width. 13 flows run. 9 bugs found, 3 candidate bugs disproved before reporting,
4 items not testable in this environment. The tester did not modify the repo, git, the `.env`,
the edge function, or the database beyond read-only selects.

## Section 1: Bugs, ranked by severity

### 1. A photo read sets the split title in the database, but the Name field keeps the old text and overwrites it on the next keystroke

**Steps.** Start a split, name it "Dinner at Joe's" (the placeholder), add a person, pick By item,
upload a receipt photo whose merchant is "Test Diner". Then type any character in the Name field.

**Expected.** The merchant replaces a placeholder title, and the Name field shows it.

**Actual.** The database row became `title = "Test Diner"` and the caption read
"Read from Test Diner, Sep 11, 7:42 pm", but the Name field still showed "Dinner at Joe's".
Typing one character wrote `title = "Dinner at Joe's!"` back to the database, discarding the
merchant with no warning. Verified by SQL before and after.

**Cause.** `SectionWho` in `src/components/Split.jsx` holds the title in
`useState(receipt.title || '')` and never re-syncs when the prop changes. The same file solves
this correctly for tax and tip with a `key={'tax' + String(receipt.tax_amount)}` remount. The
same gap means a rename made by anyone else on the link never appears here and can be
overwritten.

**Screenshot.** `C:\Users\PHILIP~1\AppData\Local\Temp\claude-chrome-screenshots-SLHbAp\screenshot-1789279653336-100.jpg`

### 2. Every payment button in a trip's "Who owes who" section is dead

**Steps.** Put two splits with different payers in one trip, open the trip page, scroll to
Who owes who, tap any of the five service buttons.

**Expected.** At minimum Venmo and Apple Cash open a prefilled message, the way they do on a
person card.

**Actual.** All ten buttons (five per row) render as
`<a class="pay v-venmo off" rel="noreferrer" aria-disabled="true">` with no href. Nothing
happens on tap. This is independent of whether anyone has payment handles saved.

**Cause.** `src/components/Trip.jsx:322` writes `const links = buildPaymentLinks(...)`, but that
function returns `{links, apps, bodies}`, so every `links[key]` lookup is undefined.
`src/components/PersonCard.jsx:110` destructures correctly. Confirmed by importing the module in
the page: the returned object's own keys are `links`, `apps` and `bodies`, `result.links.venmo`
is a valid sms URL, and `result.venmo` is undefined.

**Screenshot.** `C:\Users\PHILIP~1\AppData\Local\Temp\claude-chrome-screenshots-SLHbAp\screenshot-1789279528322-99.jpg`

### 3. Choosing a payer who is not you removes the payer picker permanently

**Steps.** On the settle screen, tap a payer chip other than yourself.

**Expected.** The payer can be changed again.

**Actual.** The screen switches to the "you owe them" view, which has no payer picker. Searching
the whole page for "Who paid the bill?" returns nothing. A mis-tap is unrecoverable from the
interface.

**Cause.** `SectionSettle` in `src/components/Split.jsx` computes
`host = !payer || !viewer || viewer.id === payer.id` and returns the non-host branch before the
picker is rendered. The picker exists only in the host branch.

**Screenshot.** `C:\Users\PHILIP~1\AppData\Local\Temp\claude-chrome-screenshots-SLHbAp\screenshot-1789279390333-97.jpg`

### 4. A friend sees "Not part of a trip" selected on a split that is in a trip, and one tap detaches it for everyone

**Steps.** Open a trip split's link on a device that did not create the trip.

**Expected.** The dropdown names the trip, or is read-only.

**Actual.** The dropdown reads "Not part of a trip" while the caption directly below reads
"Part of QA Weekend. See trip totals". The select element's value is the empty string against a
set `trip_id`. Selecting the option that already looks selected calls `chooseTrip('')` and writes
`trip_id: null`, removing the split from the trip for every viewer.

**Cause.** `SectionWho` in `src/components/Split.jsx` builds its option list from `tripIds()`,
which reads the device-local `rs.trips` key, but sets `value` from the database
`receipt.trip_id`. A device that did not create the trip has no matching option.

**Screenshot.** `C:\Users\PHILIP~1\AppData\Local\Temp\claude-chrome-screenshots-SLHbAp\screenshot-1789279268217-96.jpg`

### 5. Deleting a trip you do not own throws instead of doing anything

**Steps.** Remove a trip's entry from the `rs.tokens` map in localStorage, leaving `rs.trips`
intact, reload home, then tap Delete on the trip card (or swipe it left).

**Expected.** No Delete control at all. That is what a split row does when the device holds no
token.

**Actual.** The Delete control renders anyway, and tapping it throws
`Uncaught TypeError: onDelete is not a function` at `Landing.jsx:1025`, called from `askDelete`
at `Landing.jsx:775`. No confirmation sheet opens, nothing is deleted, and the trip stays listed.
The error fired twice, once as the React `invokeGuardedCallback` rethrow.

**Cause.** `TripCard` in `src/components/Landing.jsx` receives
`onDelete={owns(t.trip.id) ? () => removeTrip(t) : null}` from the parent, but passes
`onDelete={() => onDelete()}` down to `Swipeable`. That arrow function is always truthy, so
`Swipeable`'s `if (!onDelete) return` guard never fires even when the parent passed null, and the
wrapper then calls null. `SwipeRow` in the same file does it correctly with
`mine ? () => onDelete(id) : null`.

**Screenshot.** None. The evidence is the console stack trace, captured live.

### 6. The profile's "First choice" service is ignored on your own settle screen

**Steps.** In Your profile, add a Venmo username and a Cash App cashtag, tick Cash App as First
choice, and save. Open a split where other people owe you, and look at the single collapsed
button on each person card.

**Expected.** Cash App, since that is the declared first choice.

**Actual.** Venmo, on every card. The friend's view of the same split, opened on a device whose
profile name matches nobody, correctly leads with Cash App and then lists Venmo and PayPal, so
the setting works in one direction only.

**Cause.** `src/components/PersonCard.jsx:111` reads
`const picked = mode === 'send' ? servicesFor(target) : { list: SERVICE_ORDER, strict: false }`.
Only the send branch consults `servicesFor`, which is the function that moves the preferred
service to the front. Request mode hard-codes `SERVICE_ORDER`, which begins with Venmo.
Compounding it, `requestBody('venmo', ...)` in `src/lib/pay.js` returns a usable message even
with no Venmo handle at all, so `links.venmo` is never null in request mode and Venmo always wins
the `list.find` that picks the primary. The comment directly above line 111 states that a person
who named a first choice has it moved to the front, which is true only in send mode.

**Screenshot.** `C:\Users\PHILIP~1\AppData\Local\Temp\claude-chrome-screenshots-SLHbAp\screenshot-1789278965325-95.jpg`

### 7. Send PDF can fail silently, with no message and no download

**Steps.** On a person card, open More and tap Send PDF.

**Expected**, per the README: on a device that cannot share files, the PDF downloads, and a note
explains why.

**Actual.** `navigator.share` was wrapped to record what happened. It was called once with the
correct file (`halfsies-qa-dinner-sam.pdf`) and title (`QA Dinner`), and rejected with
`NotAllowedError: Must be handling a user gesture to perform a share request`. The download
fallback did not run and nothing reached the user.

**Scope of the claim.** That click was programmatic and therefore had no transient user
activation, so under a real finger tap the Windows share sheet very likely opens and the feature
works. A real tap was not tested. Send PDF is not being reported as broken on desktop Chrome.

The defensible finding is narrower and still real, and it has two parts. `deliverPdf` in
`src/lib/statement-pdf.js` returns `'share'` and swallows every rejection with
`.catch(() => {})`, so any failure that is not a user cancel leaves the user with no file, no
download and no message. And `navigator.canShare({files})` returns true on Windows desktop
Chrome, so `CAN_SHARE_FILES` is true, the download branch never runs, and the "An email link
cannot carry an attachment, so Send PDF downloads the file instead" note is hidden on exactly the
platform the README says needs it.

Separately verified as working: with `canShare` forced false, the download branch produced a
valid 154,971-byte `%PDF-1.3` file named `halfsies-qa-dinner-sam.pdf`, and its extracted text
reconciled to the cent (items $13.77, tax $1.38, tip $3.11, total owed $18.26).

**Screenshot.** None. The evidence is the recorded share call and its rejection name.

### 8. Home shows "No splits yet" while splits are on screen

**Steps.** From a home screen holding one trip card and one loose split, archive or delete every
loose split.

**Expected.** The trip card stands alone, or the empty line accounts for the splits inside the
trip.

**Actual.** The recent list prints "No splits yet. Start one and send the link." directly beneath
a trip card reading "QA Weekend, $104.22, 2 splits". The statement is false as displayed.
Captured page text:

```
Recent splits | QA Weekend | $104.22 | Sep 13 | A | S | K | 2 splits | Archive | Delete |
More actions | | No splits yet. Start one and send the link.
```

**Cause.** `RecentList` in `src/components/Landing.jsx` renders `EmptyState` whenever its own
`rows` array is empty. The trip groups are rendered above it by a separate `shown.trips.map`, and
`RecentList` has no knowledge of them.

**Screenshot.** None.

### 9. Two payment labels fall below the accessibility contrast minimum in light mode

**Steps.** Inspect any `.pay` button in the default light theme.

**Expected.** 4.5 to 1 against its background. The label is 14px at weight 700, which does not
meet the WCAG definition of large text (18.66px bold or 24px normal), so the relaxed 3.0
threshold does not apply.

**Actual.** Venmo and Cash App both fail. Computed against the live token values, with `.pay`
backgrounds being `var(--surface)`.

| Service | Light on #ffffff | Dark on #111a2e |
|---|---|---|
| Venmo | 3.39 | 7.09 |
| Cash App | 3.16 | 9.93 |
| PayPal | 11.85 | 5.45 |
| Zelle | 7.54 | 5.10 |
| Apple Cash | 17.85 | 14.77 |

**Cause.** The light `--venmo: #008cff` and `--cashapp: #00a82d` tokens in `src/App.css`. Dark
mode passes on every service, so light is the failing theme, which is the opposite of what a
dark-mode review would predict.

One related note, not a defect: `.pay.off { opacity: 0.45 }` drops the greyed buttons to between
2.02 and 2.98 in dark mode. That is a deliberately de-emphasised state and it behaves the same in
both themes.

**Screenshot.** None. The evidence is the computed ratio table.

### Three candidate bugs disproved rather than reported

Tax appeared not to commit on blur, which turned out to be a synthetic blur event not reaching
React's `focusout` delegation; with a real focus and blur it commits correctly. The swipe
snap-back animation appeared broken from an apparent CSS class mismatch, but the computed
transition on `.swipe-hold` is `transform 0.2s`. Section auto-scroll appeared broken, but smooth
scrolling is disabled browser-wide in this Chrome profile.

## Section 2: Copy findings

The sweep is clean on the mechanical tells. Zero em dashes, zero en dashes, zero exclamation
marks and zero emoji, both in every source string outside comments (scanned with Python across
all of `src` plus `index.html`) and in the rendered text of the home screen, the explainer page,
a full split with all five sections open, every disclosure inside a person card, and the trip
page.

Three judgment items:

- "You owes Sam $7.19" is ungrammatical. It appears on the trip page as a name line reading
  "You" above a line reading "owes Sam", and as one flat line in the trip PDF. `PersonCard`
  handles the same case correctly with "you owe". The fix belongs in the `Owed` component in
  `src/components/Trip.jsx`.
- "When your math isn't mathing, go halfsies." is the tagline. It is deliberate on the marketing
  page, but it also prints at the top of every statement PDF, including the one-person statement
  a friend receives to settle a bill. Worth a decision rather than a default.
- The mock settle screen on the explainer names Casey, Jordan and Riley. These read as
  placeholders rather than real people, flagged only for completeness.

Two design observations, not defects. A friend holding the link gets the full edit surface,
including per-item removal and the tax and tip fields, which the README frames as intended. And a
person with no saved handles gets Apple Cash as their single primary button on any device,
Android included, because `sendBody('applepay', ...)` always returns a message.

## Section 4: What could not be tested, and why

**The 390 by 844 viewport.** `resize_window` reports success but the window does not change. It
is maximized and shared with tabs belonging to other agents in this session, so it was not forced
at the operating system level. Phone width was emulated by overriding the app's own `--col` token
to 390px, and the viewport height was already 855. The one place this is not faithful is the
marketing page, whose `@media (min-width: 1024px)` block widens the hero to 560px.

**The page walking down to each newly unlocked section.** Smooth scrolling is disabled in this
Chrome profile: `window.scrollTo({top, behavior:'smooth'})` is a no-op while `behavior:'auto'`
works, and `prefers-reduced-motion` reports false. `scrollIntoView` was instrumented and the app
does call it with the correct element at each transition, so the code path fires. Whether the
page actually moves is unverifiable here.

**Dark mode rendered.** `matchMedia` cannot be forced, the Chrome extension exposes no media
emulation, and the only remaining route was changing the Windows theme, which is a system
settings change and out of scope. Injecting a mirror of the dark tokens was ruled out by the
brief. Instead the shipped `@media (prefers-color-scheme: dark)` block was read out of the CSSOM
without applying it, all 25 tokens confirmed to parse onto `:root`, and the contrast ratios
computed in bug 9. Dark mode is numerically the stronger of the two themes. No dark screenshot
exists.

**Send PDF under a real tap**, for the reason set out in bug 7.

One unverified note rather than a finding: `main.jsx` runs in `React.StrictMode`, and the scroll
effect in `Split.jsx` guards itself with a `firstPaint` ref. Under StrictMode's double effect
invocation the ref is already false on the second run, so the effect scrolls on first mount in
development but not in a production build. It could not be observed because smooth scrolling is
dead in this profile.
